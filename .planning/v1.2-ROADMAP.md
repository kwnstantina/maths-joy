# Roadmap: v1.2 Greg AI Enhancement

## Overview

Builds on the shipped Greg AI chatbot (Phase-less, commit `3f5b02b`): persistent per-user chat
(`GregChatSession`/`GregChatMessage`), SSE streaming from `api.greg-ai.tsx`, Haiku 4.5 via
`anthropic.server.ts`, Socratic system prompt, login-gated widget in `gregAiWidget.tsx`.

**Milestone goal:** turn a generic tutor bubble into a differentiated, cost-safe learning product —
students snap photos of problems, get a structured hint ladder, and are funneled toward the site's
own exercises/videos/books, while a daily quota and model tiering keep the Anthropic bill predictable.

**Status:** planned (v1.1 still active). Promote to active via `/gsd-new-milestone` when v1.1 ships.

## Phases (8–14, continuing v1.1's numbering)

| # | Phase | Priority | Effort | Depends on |
|---|-------|----------|--------|------------|
| 8 | Guardrails & Evidence | P0 | S–M | Greg AI (shipped) |
| 9 | Photo Input & Model Tiering | P1 | M | 8 |
| 10 | Contextual Tutoring | P1 | M | 8 |
| 11 | Site-Aware Tools | P2 | L | 10 |
| 12 | Personalization & Prompt Caching | P1/P2 | M | 11 |
| 13 | Practice Mode | P2 | L | 10 |
| 14 | Teacher Analytics Dashboard | P2 | M | 8, 10 |

### Sequencing rationale

Your gut order was **photo → daily cap → tools**. I put **Guardrails (Phase 8) first** — the daily
cap protects your wallet *before* photo input (which adds Opus-tier image cost), and the 👍/👎
plumbing is the evidence layer every later tuning decision (model tiering, prompt changes) depends
on. Photo input is Phase 9, immediately after. Site-aware tools stay near the front of the
"bigger features" but after Phase 10, because tools work best once the prompt is exercise-aware.
Everything past Phase 11 grows the system prompt, so **prompt caching (GREGAI-11) is bundled into
Phase 12** where it starts paying off.

## Phase Details

### Phase 8: Guardrails & Evidence
**Goal**: Greg AI is safe to launch — a student cannot run up an unbounded bill, and every answer can be rated so future tuning is evidence-based.
**Depends on**: Greg AI (shipped)
**Requirements**: GREGAI-02, GREGAI-03
**Priority / Effort**: P0 / S–M

**Success Criteria** (what must be TRUE):
1. A user who sends N messages in a day is blocked on message N+1 with a friendly localized "come back tomorrow" message, and the count resets at local midnight (or a fixed UTC boundary — decide in plan).
2. The quota persists across serverless cold starts (stored in Mongo, not the in-memory rate-limit map).
3. Each assistant message shows 👍/👎 controls; a click persists the rating against that message and visibly reflects the selection.
4. Ratings are queryable by session/topic for later analytics (Phase 14).

**Technical approach**:
- **Daily cap**: new `GregDailyUsage` model (`userId`, `date` (YYYY-MM-DD string), `count`) with a unique compound index `@@unique([userId, date])`. On each chat POST, atomically `upsert`+`increment` and compare against a `CHAT_DAILY_LIMIT` const. Return HTTP 429 with a localized body when exceeded. Keep the existing in-memory `chat` burst limiter (`ratelimit.server.ts`) as the first gate; the Mongo cap is the daily ceiling.
- **Feedback**: add `rating` (`Int?` — -1/0/1) to `GregChatMessage`, or a separate `GregMessageFeedback` model if you want multiple raters later (single-rater `rating` field is enough now). New route `api.greg-ai.feedback.tsx` (POST `{ messageId, rating }`, `getUserId` + ownership check via the message's session). Widget: 👍/👎 buttons under each assistant bubble in `gregAiWidget.tsx`, optimistic UI.

**Key files**: `prisma/schema.prisma` (+2 models/fields), `app/utils/gregChat.prisma.ts` (usage upsert, feedback write), `app/routes/api.greg-ai.tsx` (cap check), `app/routes/api.greg-ai.feedback.tsx` (new), `components/gregAi/gregAiWidget.tsx` (rating UI), locale files.

**Risks / Decisions**:
- Reset boundary: student-local midnight needs the client's timezone; simplest is a fixed UTC day — decide in plan. (Greece is UTC+2/+3, so UTC midnight ≈ 02:00–03:00 local, acceptable.)
- Quota tuning: pick a launch number (e.g. 30–50 msgs/day) and make it a single const so it's trivially adjustable; consider higher caps for purchasers later.
- Run `prisma:generate` + `prisma:push` (shared DB write — user-gated, per existing project convention).

### Phase 9: Photo Input & Model Tiering
**Goal**: A student can photograph an exercise and get help on it, and image/hard conversations are routed to a stronger model automatically.
**Depends on**: Phase 8
**Requirements**: GREGAI-01, GREGAI-10
**Priority / Effort**: P1 / M

**Success Criteria**:
1. Student can capture a photo (mobile camera) or select an image file in the widget, see a thumbnail preview, and send it with or without accompanying text.
2. The image is delivered to the model as an image content block and Greg AI's reply references the pictured problem.
3. Oversized/unsupported images are rejected client-side and server-side with a localized error, and each image counts toward the daily cap (Phase 8).
4. When an image is attached (or the conversation exceeds a turn threshold), the request is served by the stronger model; plain short chats stay on Haiku — verifiable via `usage`/logs.

**Technical approach**:
- **Client**: `<input type="file" accept="image/*" capture="environment">` in the widget; read as base64 (downscale client-side with a canvas to cap dimensions, e.g. ≤1568px long edge, before upload to control tokens). Preview + remove-before-send. Send as `{ message, imageBase64, imageMediaType }` in the existing JSON POST.
- **Server**: in `api.greg-ai.tsx`, when an image is present, build a multimodal user turn: `content: [{ type: "image", source: { type: "base64", media_type, data } }, { type: "text", text }]`. Validate media type (png/jpeg/webp) and decoded size (≤ ~5MB) server-side. Persist a marker in `GregChatMessage` (store a short "[image]" note or a Cloudinary URL if you want history thumbnails — decide; base64 in Mongo is heavy, prefer Cloudinary upload reusing `cloudinary.server.ts`).
- **Model tiering**: `pickModel({ hasImage, turnCount })` in `anthropic.server.ts` returning Haiku by default, Opus when `hasImage || turnCount > N`. One-line switch per request. Note: switching models mid-conversation invalidates prompt cache (relevant once Phase 12 lands).

**Key files**: `components/gregAi/gregAiWidget.tsx` (capture/preview/validation), `app/routes/api.greg-ai.tsx` (multimodal turn, model pick), `app/utils/anthropic.server.ts` (`pickModel`, model consts), `app/utils/cloudinary.server.ts` (optional image persistence), `gregChat.prisma.ts` (store image ref), locales.

**Risks / Decisions**:
- **History replay**: if images are stored only as base64 and re-sent every turn, token cost balloons. Decision: upload to Cloudinary, store URL, and only include the image in the turn it was sent (subsequent turns reference text). Confirm Haiku/Opus accept URL image sources or keep base64 for the single turn.
- Camera capture UX differs iOS/Android — test on real devices.
- Opus cost per image is materially higher; the daily cap (Phase 8) is the backstop.

### Phase 10: Contextual Tutoring
**Goal**: Greg AI knows exactly which exercise/topic the student is on, greets them about it, and offers a structured hint ladder instead of caving to "just give me the answer."
**Depends on**: Phase 8
**Requirements**: GREGAI-04, GREGAI-05
**Priority / Effort**: P1 / M

**Success Criteria**:
1. On an exercise/training/book page, opening the widget shows a context-aware opener naming the current item (e.g. "Θέλεις βοήθεια με «<exercise title>»;").
2. The system prompt for that session includes the exercise's title/topic/level, so hints are specific without the student re-typing the problem.
3. The message input area offers hint-ladder actions ("Δώσε μου hint" → "Άλλο ένα" → "Δείξε μου τη λύση"), each sending a hidden directive that escalates disclosure.
4. Hint depth per session/topic is recorded (feeds Phase 14).

**Technical approach**:
- **Context**: today `deriveRouteContext(pathname)` returns a generic string. Extend the widget to read the current route's loader data (or accept props from the page) to get the actual exercise id/title/topic/level. Pass a richer `routeContext` object to the POST; `buildSystemPrompt` appends a "Current exercise: <title> — <topic>, <level>" block. For exercise pages, the loader already has the exercise (`exersices.prisma.ts`).
- **Hint ladder**: UI buttons map to hidden user directives (not shown verbatim in the transcript, or shown as a compact chip): e.g. `hint_1` → "Give one small nudge, no solution"; `hint_2` → "Give a bigger hint"; `reveal` → "Now show the full step-by-step solution." Track a per-session `hintDepth` counter; persist the max depth reached on the message/session.
- Store hint depth on `GregChatMessage` (`hintLevel Int?`) or session aggregate.

**Key files**: `components/gregAi/gregAiWidget.tsx` (context wiring, ladder buttons), `app/utils/anthropic.server.ts` (`buildSystemPrompt` extension), `app/routes/api.greg-ai.tsx` (accept structured context + directive), `gregChat.prisma.ts` (hint depth), exercise/training/book route loaders (expose title/topic to the widget), locales.

**Risks / Decisions**:
- How the widget gets page data: cleanest is the page passing props to `<GregAiWidget context={...}>` rather than the widget guessing from the URL. Requires threading context from route components → root layout, or a small context provider. Decide in plan.
- Keep hidden directives server-authoritative (don't trust client to set "reveal solution" arbitrarily — it's fine here since it's the student's own learning, but log it).

### Phase 11: Site-Aware Tools
**Goal**: Greg AI answers "I don't understand X" with a hint *plus* real links to the site's exercises, videos, and books on that topic.
**Depends on**: Phase 10
**Requirements**: GREGAI-06
**Priority / Effort**: P2 / L

**Success Criteria**:
1. Greg AI can call `search_exercises`, `search_videos`, and `find_book` tools that query the existing Prisma data-access modules.
2. A topic question yields a hint and, when relevant content exists, concrete links (e.g. "υπάρχει βίντεο και 3 ασκήσεις — [links]").
3. Tool calls stream correctly through the existing SSE pipeline without breaking the delta/append UX.
4. Tools return only published/active content and never leak admin-only fields.

**Technical approach**:
- Move from raw `anthropic.messages.stream` to the **tool-use loop** (SDK tool runner or a manual loop) in `api.greg-ai.tsx`. Define tools whose handlers call `exersices.prisma.ts`, `video.prisma.ts`, `books.prisma.ts` with locale-aware queries (`i18n.server.ts` helpers) and return compact JSON (title, url, level/topic). Render returned links as message content.
- Streaming + tool calls: handle `tool_use` stop reason, execute handler, feed `tool_result` back, continue streaming. The SSE `send("delta"/"done")` contract stays; add a `tool` event if you want to show "searching…" UX.
- Guardrails: cap tool iterations; tools read-only; enforce active/published filters.

**Key files**: `app/routes/api.greg-ai.tsx` (tool loop), `app/utils/anthropic.server.ts` (tool defs), `app/utils/exersices.prisma.ts` / `video.prisma.ts` / `books.prisma.ts` (search helpers, likely new query fns), `app/utils/i18n.server.ts` (localized content), `components/gregAi/gregAiWidget.tsx` (link rendering, optional tool-activity indicator).

**Risks / Decisions**:
- The system prompt grows (tool descriptions) — this is the trigger for **prompt caching (Phase 12)**.
- Tool loop adds latency + token cost; Haiku handles tools but multi-step reasoning may want Opus (ties to Phase 9 tiering).
- Keep tool result payloads small to avoid blowing context.

### Phase 12: Personalization & Prompt Caching
**Goal**: Greg AI adapts to the individual student using `UserProgress`, and the now-large system prompt is cached to control cost/latency.
**Depends on**: Phase 11
**Requirements**: GREGAI-07, GREGAI-11
**Priority / Effort**: P1 (caching) / P2 (personalization) / M

**Success Criteria**:
1. The system prompt includes a one-line student summary derived from `UserProgress` (level, completed units, weak areas) when available.
2. Difficulty/references in Greg AI's answers visibly reflect the student's level (spot-checkable).
3. With the enlarged system prompt, `cache_control` is applied to the stable prefix and `usage.cache_read_input_tokens` is non-zero on repeat turns.
4. (Optional) Greg AI can persist a short observation back to the student's profile/memory.

**Technical approach**:
- **Personalization**: read `UserProgress` for the user in `api.greg-ai.tsx`; build a compact summary and inject as a stable system block. Keep it deterministic (no timestamps) so it's cacheable.
- **Caching**: once system prompt (persona + tool defs + profile) exceeds the model's cacheable minimum (Haiku 4.5 = 4096 tokens; Opus = 4096), add `cache_control: { type: "ephemeral" }` on the last stable system block; keep volatile parts (route/exercise context) *after* the breakpoint. Verify with `cache_read_input_tokens`. Note the current correct comment at `api.greg-ai.tsx` about the prompt being sub-4096 today — revisit exactly here.
- **Memory writeback** (optional/stretch): a `record_observation` tool or a post-session summarizer writing to a `GregStudentNote` model; surface in future sessions. Gate behind privacy review.

**Key files**: `app/routes/api.greg-ai.tsx` (profile read, cache breakpoints, model-aware caching), `app/utils/anthropic.server.ts` (system-prompt assembly, cache config), `progress.server.ts`/`UserProgress` access, `prisma/schema.prisma` (optional `GregStudentNote`).

**Risks / Decisions**:
- **Cache invalidation**: per-student profile in the prefix means the cache is per-student (still fine — repeated turns in one session reuse it). Model switching (Phase 9) invalidates cache — keep tiering decisions in mind.
- Privacy: writing observations about minors is sensitive — disclose and consider opt-out.

### Phase 13: Practice Mode
**Goal**: A student can ask for practice problems on a topic, answer them, and get step-by-step checking — rendered as real exercise cards, not chat text.
**Depends on**: Phase 10
**Requirements**: GREGAI-08
**Priority / Effort**: P2 / L

**Success Criteria**:
1. "Δώσε μου 3 ασκήσεις στις παραγώγους" produces N generated problems returned as structured JSON.
2. Problems render as exercise-card UI (reusing existing card components), not raw chat text.
3. The student submits an answer per problem and Greg AI checks it step by step, marking correct/incorrect with guidance.
4. Malformed generations are caught (schema validation) and retried/handled gracefully.

**Technical approach**:
- Use **structured outputs** (`output_config.format` / `messages.parse`) so generated problems come back as a typed array (`{ prompt, latex, answer, steps }`). Render via the existing exercise card components (`components/card/` / exercise UI). Checking: send the student's answer + the problem back for step-by-step evaluation (structured verdict).
- Distinct UI mode in the widget (a "practice" panel) vs normal chat, or an inline card list within the chat stream.

**Key files**: `components/gregAi/gregAiWidget.tsx` (practice panel/cards), `app/routes/api.greg-ai.tsx` or a new `api.greg-ai.practice.tsx` (generation + checking with structured outputs), `app/utils/anthropic.server.ts` (schemas), reuse `components/card/`.

**Risks / Decisions**:
- Generated math correctness — Haiku may produce wrong answers/steps; consider Opus for generation, or verify generated answers programmatically where possible.
- Structured outputs support: confirm model support (Haiku 4.5 supports structured outputs; Opus does too).
- Scope creep: keep v1 to generate-answer-check; don't persist generated problems into the real exercise catalog yet.

### Phase 14: Teacher Analytics Dashboard
**Goal**: Greg (the human) sees which topics generate the most questions, where students get stuck, and at what hint depth they give up — to decide what content to make next.
**Depends on**: Phase 8, Phase 10
**Requirements**: GREGAI-09
**Priority / Effort**: P2 / M

**Success Criteria**:
1. An admin-only page aggregates chat sessions by topic/route context, message volume, and 👎 rate.
2. It surfaces hint-depth distribution (how often students escalate to "show solution") per topic.
3. Access is restricted to admins (`isAdmin` from `roles.ts`) and the privacy policy discloses that chats may be reviewed.
4. The dashboard is read-only aggregation (no PII beyond what admins already see).

**Technical approach**:
- New admin route (e.g. `admin.greg-ai.tsx`) guarded by `requireUserId` + `isAdmin`. Aggregate over `GregChatSession`/`GregChatMessage` (+ `rating`, `hintLevel`, route/exercise context stored in earlier phases) with Prisma groupBy/aggregation. Render simple charts/tables (respect the dataviz guidance if adding charts).
- Depends on Phase 8 (ratings) and Phase 10 (topic context + hint depth) actually being recorded.

**Key files**: `app/routes/admin.greg-ai.tsx` (new), `app/utils/gregChat.prisma.ts` (aggregation queries), `app/utils/roles.ts` (admin gate), `app/routes/privacyPolicy.tsx` (disclosure), locales.

**Risks / Decisions**:
- **Privacy/legal**: reviewing minors' chats must be disclosed (privacy policy) before shipping — treat as a blocking sub-task.
- Aggregation cost on Mongo — index the fields you group by (topic/route context, date).

## Open questions to resolve before planning individual phases

1. **Daily cap number + reset boundary** (Phase 8) — launch value and UTC vs local midnight.
2. **Image persistence** (Phase 9) — Cloudinary URL vs base64-in-Mongo; single-turn vs replayed.
3. **Widget↔page context wiring** (Phase 10) — props/provider vs URL-only; how the widget gets the current exercise.
4. **Model tiering thresholds** (Phase 9) — turn count / trigger conditions for Opus.
5. **Privacy policy update** (Phases 12, 14) — memory writeback + chat review disclosure; opt-out?
6. **Structured output model** (Phase 13) — Haiku vs Opus for problem generation quality.

## Recommended build order

**Phase 8 → 9 → 10 → 11 → 12 → 13 → 14.** 8 first (protect wallet + evidence), 9 next (biggest
student-facing wow), 10 to make tutoring genuinely contextual, then the differentiators. 13 and 14
can slip or run in parallel once 8/10 are in. Use `/gsd-plan-phase 8` to generate the task-level
PLAN for the first phase when ready.
